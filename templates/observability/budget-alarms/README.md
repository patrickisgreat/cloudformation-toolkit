# `observability/budget-alarms`

The first stack to deploy in a new account: a monthly cost budget that emails
you on the way up, and Cost Anomaly Detection for the spend you did not plan.

## Usage

```bash
./bin/cfn deploy observability/budget-alarms --env dev \
  --param MonthlyBudgetUsd=100 --param AlertEmail=billing@example.com
```

## A budget notifies; it does not cap

AWS Budgets cannot stop spend. What this template buys is **time**: the
forecast notification fires when the projected month crosses the line, usually
days before the actual-spend thresholds do, which is when you can still do
something about it. Budget Actions (which can attach a deny policy) are
deliberately not here; a deny policy that fires mid-deploy is its own outage.

## Set the budget to what you intend to spend

Every threshold is a percentage of `MonthlyBudgetUsd`. Set it to the bill you
expect, not the bill you fear: a budget high enough never to fire is one that
tells you nothing. The defaults (50%, 80% actual; 100% forecast) are two warnings
on the way up and one at the line.

Forecasts need about five weeks of billing history, so in a brand-new account the
forecast notification is quiet until then. The actual thresholds work from day
one.

## Email works immediately; SNS needs a policy

Budgets emails `AlertEmail` directly, with no confirmation link — unlike an SNS
email subscription. `AlarmTopicArn` is the optional second channel for paging or
chat, and the topic's own access policy must allow the service to publish:

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "budgets.amazonaws.com" },
  "Action": "SNS:Publish",
  "Resource": "<topic arn>",
  "Condition": { "StringEquals": { "aws:SourceAccount": "<account id>" } }
}
```

[`messaging/sns-topic`](../../messaging/sns-topic) does this with
`AllowPublishFromService=budgets.amazonaws.com`. Without the statement the stack
still creates and the topic silently receives nothing.

## Anomaly detection is free, and one-per-account

Cost Anomaly Detection costs nothing, so it defaults on. It watches per-service
spend and emails a daily digest of anomalies whose total impact is at least
`AnomalyThresholdUsd`. The threshold is in dollars, not percent, because a
percentage fires every time a two-dollar service doubles.

**Known limitation (why this is `beta`):** an account may hold only one
service-dimension monitor. The first stack in an account creates it; every later
stack in the same account must set `EnableAnomalyDetection=false` or its create
fails. A `beta` label until a monitor-sharing parameter lands.

See [`examples/basic`](examples/basic) for a parameter set you can deploy as-is.

### Parameters

| Parameter | Description | Type | Default |
|-----------|-------------|------|---------|
| `NamePrefix` | Prefix for the budget and monitor names. Must be unique per account, since budget names collide across stacks. | `String` | **required** |
| `Environment` | Environment this budget guards. Used in names only; the budget itself is account-wide.<br>Allowed: `dev`, `staging`, `prod` | `String` | `dev` |
| `MonthlyBudgetUsd` | The month's expected bill in USD. Not a cap - AWS Budgets only notifies - but the number every threshold below is a percentage of. Set it to what you intend to spend, not what you fear; a budget set high enough never to fire is a budget that never fires. | `Number` | `100` |
| `ActualThresholdPercent1` | First actual-spend notification, as a percentage of the budget. Fires once per month when month-to-date spend crosses it. | `Number` | `50` |
| `ActualThresholdPercent2` | Second actual-spend notification, as a percentage of the budget. | `Number` | `80` |
| `ForecastThresholdPercent` | Forecast notification, as a percentage of the budget. AWS projects the month's total from spend so far; this fires when the projection crosses the line, usually days before the actual thresholds do. Forecasts need about five weeks of history, so in a new account this one is quiet at first. | `Number` | `100` |
| `AlertEmail` | Address that receives every notification. Budgets emails directly - no confirmation link, unlike an SNS email subscription - so this works from the moment the stack completes. | `String` | **required** |
| `AlarmTopicArn` | SNS topic ARN to notify as well, for paging or chat integrations. The topic's own policy must allow budgets.amazonaws.com to publish (see the README); without that statement the stack still creates and the topic silently receives nothing. Leave empty for email only. | `String` | `""` |
| `EnableAnomalyDetection` | Create a Cost Anomaly Detection monitor over per-service spend with a daily email digest. The service is free. An account may hold only ONE service-dimension monitor, so set this to false in every stack after the first in the same account.<br>Allowed: `true`, `false` | `String` | `true` |
| `AnomalyThresholdUsd` | Smallest anomaly, in USD of total impact, worth an email. Below a few dollars the digest is noise from normal day-to-day variance. | `Number` | `20` |
