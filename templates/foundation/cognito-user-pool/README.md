# `foundation/cognito-user-pool`

A Cognito user pool for SPA and mobile sign-in: email as the username, SRP-only
auth flows, a public app client, and defaults chosen so the pool you get by
passing nothing is the one you would defend in review.

## Usage

```bash
./bin/cfn deploy foundation/cognito-user-pool --env dev \
  --param CallbackUrls=http://localhost:3000/callback
```

Wired to `serverless/http-api`, whose JWT authorizer takes exactly this pool's
outputs:

```yaml
Api:
  Type: AWS::CloudFormation::Stack
  Properties:
    TemplateURL: ../../templates/serverless/http-api/template.yaml
    Parameters:
      NamePrefix: !Ref NamePrefix
      Environment: !Ref Environment
      LambdaFunctionArn: !GetAtt Fn.Outputs.FunctionArn
      JwtIssuer: !GetAtt Auth.Outputs.ProviderUrl
      JwtAudience: !GetAtt Auth.Outputs.WebClientId
```

## The defaults that will surprise someone

**Self-signup is off.** By default only an administrator can create users, who
then receive an invitation email. A pool that quietly accepts signups is an open
directory anyone can join — right for a consumer product, wrong for everything
else. Consumer products set `AllowSelfSignUp=true` deliberately.

**The app client has no secret, and that is correct.** A secret compiled into a
JS bundle or mobile binary is published, not protected. The client uses SRP
(the password is proved, never transmitted) and the OAuth code flow; the
plaintext `USER_PASSWORD_AUTH` flow is deliberately absent, so an SDK
configured for it will fail — reconfigure the SDK, don't add the flow.

**Sign-in errors are deliberately vague.** `PreventUserExistenceErrors` makes
"no such user" and "wrong password" indistinguishable, so the login form cannot
be used to enumerate who has an account. If you are debugging "why can't this
user sign in", this is why the error doesn't say.

## The user directory cannot be deleted by accident

The pool carries `DeletionPolicy: Retain`, `UpdateReplacePolicy: Retain`, and
`DeletionProtection: ACTIVE`. The second one matters most: several innocuous-
looking properties (`Schema`, `UsernameAttributes`) **replace the pool on
change**, and a replaced pool is every user gone — usernames, passwords, MFA
enrollments. Tearing a pool down for real is a two-step: disable deletion
protection in the console or CLI, then delete.

## Known limitation: email volume (why this is beta)

Email — invitations, verification codes, password resets — goes through
Cognito's built-in sender, capped at roughly **50 messages a day** and sent
from `no-reply@verificationemail.com`. Fine for dev and small teams; a
production sign-up flow needs SES (`EmailSendingAccount: DEVELOPER`), which
this template does not model yet. When the cap is hit, sends fail silently
from the user's point of view — "I never got the code" is the symptom.

## MFA and the escape hatches

TOTP (authenticator app) MFA is offered but not required (`OPTIONAL`). `ON`
requires it for everyone — turn that on early if you want it, because moving
`OFF → ON` later forces every existing user through enrollment at their next
sign-in. SMS MFA is not offered at all: it needs an SNS role, costs per
message, and is the weaker factor.

`HostedUiDomainPrefix` adds a Cognito-hosted sign-in page (needed for the OAuth
redirect flow without building your own form). The prefix is globally unique
across all AWS accounts, so `login` is taken; `<team>-<app>-auth` is not.

See [`examples/basic`](examples/basic) for a parameter set you can deploy as-is.
