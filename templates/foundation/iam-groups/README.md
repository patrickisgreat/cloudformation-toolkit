# foundation/iam-groups

The standing permission tiers for human IAM users: `<prefix>-admins`,
`<prefix>-powerusers`, `<prefix>-readonly`, each individually optional, plus a
custom group defined by whatever managed policy ARNs you hand it. Users join
these groups through `foundation/iam-user` stacks — this template creates no
users and no credentials.

> **Is IAM the right tool?** For a team of any size across multiple accounts,
> AWS Identity Center (SSO) is the better answer — short-lived credentials, one
> login, no per-account users. IAM groups and users are the right size for a
> single account or two with a handful of humans, which is exactly the setup
> this library's `environments/` model serves.

## The decisions that matter

**MFA enforcement is on by default, and it changes day one for new users.**
Every created group gets a policy that denies everything except MFA
self-enrolment until the session carries MFA. A brand-new user's first login
can do exactly one thing: add an MFA device (then sign in again). If you skip
this template's `iam-user` and create users by hand, attach
`MfaEnforcementPolicyArn` yourself or those users bypass the requirement.

The deny deliberately does **not** exempt `iam:DeactivateMFADevice` or
`iam:DeleteVirtualMFADevice`: stolen access keys must not be enough to remove
the second factor. The flip side: a user who loses their device needs an admin
to deactivate it for them.

**The deny uses `BoolIfExists`, not `Bool`.** Requests signed with long-lived
access keys carry no `aws:MultiFactorAuthPresent` key at all. A plain `Bool`
condition would not match those requests, and the deny would silently not
apply to exactly the credential type most likely to leak.

**No environments here, on purpose.** IAM is account-global. If you want
dev-humans separated from prod-humans, that is what separate accounts are for
— see `foundation/org-account`.

## Usage

```bash
./bin/cfn deploy foundation/iam-groups --env dev
```

Then feed the group-name outputs to `foundation/iam-user` stacks' `Groups`
parameter. A custom tier is one parameter:

```bash
./bin/cfn deploy foundation/iam-groups --env dev \
  --param CustomGroupSuffix=billing \
  --param CustomGroupManagedPolicyArns=arn:aws:iam::aws:policy/job-function/Billing
```

## Failure modes

- *"I created a user and they can't do anything."* Working as intended until
  they enrol MFA. The console shows `AccessDenied` on everything; the fix is
  IAM → My security credentials → Assign MFA device, then a fresh sign-in.
- *"CLI calls fail even after console MFA."* Long-lived key requests carry no
  MFA. The user must call `aws sts get-session-token --serial-number ...
  --token-code ...` and use the returned temporary credentials.
