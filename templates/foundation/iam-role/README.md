# foundation/iam-role

A general-purpose IAM role. Two trust knobs — an AWS service principal, a list
of AWS principals (cross-account) — and three permission knobs: managed policy
ARNs, a raw inline policy document, and a permissions boundary. Most roles in
this library are created by the template that needs them; this one is for the
roles that belong to no other template — deployment execution roles,
cross-account access roles, break-glass roles, vendor-access roles.

## The decisions that matter

**`RequireMfa` defaults to `true`, and it will fail your machine-to-machine
role until you turn it off.** Cross-account trust is usually for humans, and a
human-assumable role without MFA is one leaked password from account access.
But `aws:MultiFactorAuthPresent` is never true for role-chaining or service
credentials, so a role assumed by another role must set `RequireMfa: false`.
The failure looks like an `AccessDenied` on `sts:AssumeRole` even though the
principal is listed in the trust policy.

**A role nobody can assume fails at deploy time, on purpose.** Leaving both
`ServicePrincipal` and `TrustedPrincipalArns` empty trips a template `Rules`
assertion before any resource is created, because IAM would otherwise reject
the empty trust policy mid-create and roll back.

**`InlinePolicyJson` is the escape hatch, not the main path.** Parameters cap
at 4096 characters. A policy that outgrows that — or that two roles share —
should become a customer managed policy and arrive via `ManagedPolicyArns`.

**`ExternalId` is for third parties.** When a vendor's account assumes this
role, the ExternalId condition is what stops another customer of the same
vendor from steering the vendor's role into your account (the confused-deputy
problem). It is not a secret and not a substitute for MFA.

## Usage

```bash
./bin/cfn deploy foundation/iam-role --env dev \
  --param RoleSuffix=cfn-exec \
  --param ServicePrincipal=cloudformation.amazonaws.com \
  --param RequireMfa=false
```

The `RoleArn` output goes wherever the role is consumed: `--role-arn` on a
CloudFormation deploy, `role-to-assume` in a workflow, `TrustedPrincipalArns`
of another role.

## Recipes

A CloudFormation **deployment execution role** — pass it to
`aws cloudformation create-stack --role-arn` (or a change set) so deploys run
with scoped permissions instead of the caller's:

```json
[
  { "ParameterKey": "NamePrefix",       "ParameterValue": "myapp" },
  { "ParameterKey": "RoleSuffix",       "ParameterValue": "cfn-exec" },
  { "ParameterKey": "ServicePrincipal", "ParameterValue": "cloudformation.amazonaws.com" },
  { "ParameterKey": "ManagedPolicyArns","ParameterValue": "arn:aws:iam::aws:policy/PowerUserAccess" },
  { "ParameterKey": "RequireMfa",       "ParameterValue": "false" }
]
```

This pairs with `foundation/github-oidc-role`: the OIDC role holds only the
permission to drive CloudFormation, and this role holds the permission to
create resources.

A **cross-account read-only role** for a human operator in another account:

```json
[
  { "ParameterKey": "NamePrefix",           "ParameterValue": "myapp" },
  { "ParameterKey": "RoleSuffix",           "ParameterValue": "auditor" },
  { "ParameterKey": "TrustedPrincipalArns", "ParameterValue": "arn:aws:iam::123456789012:root" },
  { "ParameterKey": "ManagedPolicyArns",    "ParameterValue": "arn:aws:iam::aws:policy/ReadOnlyAccess" }
]
```

`RequireMfa` stays on its default here — the operator must MFA before
assuming.
