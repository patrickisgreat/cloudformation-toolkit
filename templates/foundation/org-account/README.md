# foundation/org-account

Account vending: one stack, one member account in your AWS Organization,
placed in an OU and reachable through `OrganizationAccountAccessRole`. This is
how "spin up a new environment" stops meaning "share an account and hope IAM
keeps things apart" — the account boundary is the only isolation AWS never
pokes holes in.

**Beta:** this template creates and places the account. It does not model OUs
or SCPs themselves — pass an existing `ParentOuId` — and it does not delegate
Organizations administration. Both are candidates once real usage shows the
shape.

## Before the first deploy

- Deploy from the **management account**, with the organization in
  All-Features mode. Anywhere else, the create fails with
  `AccessDeniedException`.
- Organizations processes **one account creation at a time**. Two org-account
  stacks deployed concurrently will throw
  `ConcurrentModificationException`; deploy them serially.

## The decisions that matter

**Email is forever.** Root email addresses are globally unique across all of
AWS, including closed accounts, and changing one replaces the account.
Plus-addressing (`aws+dev@example.com`, `aws+prod@example.com`) gives every
account its own address in one inbox. Decide the scheme before the first
account, not after the fifth.

**Deleting the stack does not close the account — by design.** `Retain` on
both policies means a rollback or a stack delete leaves the account running.
Closing an account is `aws organizations close-account`: it suspends for 90
days, counts against a quota of closures, and takes the account's data with it
at the end. No template should be able to do that as a side effect.

**OU placement is SCP inheritance.** An empty `ParentOuId` lands the account
in the organization root, where only the root's policies apply. If you have a
workloads OU with guardrails, pass it — moving the account later works but is
a manual `move-account`, not a stack update (`ParentIds` changes are not
supported for accounts created before the property existed; keep it set from
day one).

## Usage

```bash
./bin/cfn deploy foundation/org-account --env prod   # from the management account
```

After the deploy, the `AccessRoleArn` output is the way in:

```bash
aws sts assume-role --role-arn <AccessRoleArn> --role-session-name bootstrap
```

From there, the usual bootstrap order is `foundation/github-oidc-role` (so CI
can reach the account), then `foundation/iam-groups` + `foundation/iam-user`
if humans need direct access, then an `environments/<env>/` entry pointing at
the new account ID.

### Parameters

| Parameter | Description | Type | Default |
|-----------|-------------|------|---------|
| `NamePrefix` | Prefix for the account name, normally the org name. | `String` | **required** |
| `AccountSuffix` | What this account is for. The account name becomes <NamePrefix>-<AccountSuffix>, e.g. example-org-dev or example-org-workloads-prod. One account per environment is the model this library's environments/ directory assumes. | `String` | **required** |
| `Email` | Root email for the new account - globally unique across all of AWS, forever, including closed accounts. Plus-addressing is the standard trick: aws+dev@example.com and aws+prod@example.com are distinct to AWS and one inbox to you. This property cannot be changed later without replacing the account. | `String` | **required** |
| `ParentOuId` | Organizational unit to place the account in (ou-xxxx-xxxxxxxx), or a root ID (r-xxxx). Leave empty for the organization root. Placement decides which SCPs apply, so "empty" means "no guardrails beyond the root's". | `String` | `""` |
| `AccessRoleName` | Name of the admin role Organizations pre-creates in the new account, assumable from the management account. Keep the default unless your org standardised on another name; every tool that says "assume OrganizationAccountAccessRole" assumes the default. | `String` | `OrganizationAccountAccessRole` |
