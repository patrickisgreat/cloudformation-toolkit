# foundation/iam-user

One IAM user per stack. Permissions come from group memberships (see
`foundation/iam-groups`); credentials are opt-in, and when opted into they are
born inside Secrets Manager — the password by `GenerateSecretString`, the
access key by `GetAtt` straight into a secret. Nothing secret ever appears in
a parameter, an output, a change set, or a CI log.

One stack per user is the point, not an inefficiency: onboarding is a deploy,
offboarding is a stack delete, and the account's human roster is `aws
cloudformation list-stacks`.

## The decisions that matter

**Both credential types default to off.** A user with no password and no key
is just a name with group memberships — useful as a principal for trust
policies, immune to phishing. Turn on `EnableConsoleAccess` for humans who
use the console; leave `CreateAccessKey` off unless a specific tool cannot do
roles or SSO.

**The console password is single-use by design.** It lands in
`iam/<prefix>-<user>/console-password`, and `PasswordResetRequired` forces a
change at first sign-in — so the stored copy stops working the moment the
human starts. That is also why the secret is *not* retained on stack delete,
unlike `foundation/secret`: it holds nothing durable.

**The access key's secret half exists in exactly one place** —
`iam/<prefix>-<user>/access-key`, written by `GetAtt` inside the template.
Rotating it is: set `CreateAccessKey` to `false`, deploy, set it back to
`true`, deploy. The old key dies with the first update, the new pair appears
in the same secret name.

**If the user's groups came from `foundation/iam-groups` with MFA enforcement
on** (the default), their first session can only enrol an MFA device. Tell
them that, or their first hour is an `AccessDenied` mystery — the groups
README has the day-one script.

## Usage

Onboarding, end to end:

```bash
./bin/cfn deploy foundation/iam-user --env prod   # with alice's parameter file
aws secretsmanager get-secret-value \
  --secret-id iam/example-org-alice/console-password --query SecretString
# hand the password to alice out of band, with the ConsoleSignInUrl output
```

### Parameters

| Parameter | Description | Type | Default |
|-----------|-------------|------|---------|
| `NamePrefix` | Prefix for the user name, normally the org or team name. | `String` | **required** |
| `UserName` | The human's identifier, e.g. "alice". The IAM user becomes <NamePrefix>-<UserName>. One stack per user - deleting the stack offboards exactly one person. | `String` | **required** |
| `Groups` | Comma-separated IAM group names this user joins - the outputs of a foundation/iam-groups stack, e.g. "example-org-powerusers". Groups are where permissions should come from; leave ManagedPolicyArns empty unless this user genuinely needs something no group grants. | `String` | `""` |
| `ManagedPolicyArns` | Comma-separated managed policy ARNs attached directly to the user. The escape hatch, not the main path: per-user policies are what makes an account unauditable. Leave empty for none. | `String` | `""` |
| `PermissionsBoundaryArn` | Optional permissions boundary capping everything the user's groups and policies grant. Leave empty for none. | `String` | `""` |
| `EnableConsoleAccess` | Give the user a console password. It is generated by Secrets Manager, never appears in the template or the change set, and must be changed at first sign-in. Off by default: a user who only ever assumes roles or uses SSO needs no password at all.<br>Allowed: `true`, `false` | `String` | `false` |
| `CreateAccessKey` | Create a long-lived access key, stored in Secrets Manager. Off by default because long-lived keys are the credential that leaks: prefer roles (foundation/iam-role) or the CLI's SSO support. Turn on only for the tool that supports nothing else.<br>Allowed: `true`, `false` | `String` | `false` |
