# `container-service`

A whole working web service from one parameter set: VPC, ECR repository, ECS
cluster, load balancer, TLS certificate, DNS record, autoscaling Fargate service,
alarm topic and alarms.

This is the archetype most server applications collapse into — Go, Rust, C++,
Java, Kotlin, C#/.NET, Node, TypeScript, Python, GraphQL servers, REST and gRPC
APIs. See [docs/ARCHETYPES.md](../../docs/ARCHETYPES.md) for the mapping.

## Usage

```bash
./bin/cfn deploy container-service --env dev
```

Requires `artifacts_bucket` in `environments/<env>/env.json` — the stack uses
nested stacks, so `bin/cfn` runs `aws cloudformation package` first to upload the
child templates.

## The first deploy is a chicken-and-egg

This stack **creates** the ECR repository your image will live in, so on the
first deploy that repository is empty and `ImageUri` has nothing to point at.

The sequence that works:

```bash
# 1. Deploy with a public placeholder so the stack completes
./bin/cfn deploy container-service --env dev \
  --param ImageUri=public.ecr.aws/nginx/nginx:stable --param ContainerPort=80

# 2. Push your image to the repository the stack created
./bin/cfn outputs container-service --env dev     # note RepositoryUri
docker build -t $REPO:$(git rev-parse --short HEAD) .
docker push $REPO:$(git rev-parse --short HEAD)

# 3. Deploy for real
./bin/cfn deploy container-service --env dev --param ImageUri=$REPO:$SHA
```

From then on a deploy is one command with a new `ImageUri`. Alternatively, split
the registry into its own long-lived stack — see "Splitting it up" below.

## What you get

```
Internet
   |
   v
Route 53 alias  ->  ALB (public subnets, TLS 1.3/1.2, HTTP->HTTPS redirect)
                      |  listener rule: host = DomainName
                      v
                    Fargate tasks (private subnets, autoscaled 2..10)
                      |  task security group admits the ALB only
                      v
                    CloudWatch Logs + alarms -> SNS
```

Every child is a template from `templates/`, wired by outputs. Nothing is defined
inline in this stack — a resource that exists only inside a composition is one
nobody can reuse, and it escapes the per-template test suites.

## The parameters that matter

**`DomainName` must be inside `HostedZoneId`.** The certificate is DNS-validated,
so if the zone is not authoritative for the domain the validation record is
written, never resolves, and the whole stack sits in `CREATE_IN_PROGRESS` until
it times out. This is the most common way this stack appears to hang.

**`HealthCheckPath` must not depend on a database.** A health endpoint that
checks its dependencies turns a slow database into a total outage: every target
fails the check, every target is removed, and the service that was merely
degraded is now down.

**`NatGatewayMode`** is the largest fixed cost here — `single` is roughly
$32/month, `per-az` multiplies it by the AZ count. See
[`foundation/vpc`](../../templates/foundation/vpc) for the trade-off.

**`AlarmEmail`** produces a subscription that stays **pending** until someone
clicks the confirmation link. Until then the alarms are silent while the stack
reports healthy.

## Adding a database

The stack outputs everything a database stack needs:

```bash
./bin/cfn deploy database/aurora-serverless-v2 --env dev \
  --param VpcId=<VpcId> \
  --param SubnetIds=<PrivateSubnetIds> \
  --param ClientSecurityGroupId=<TaskSecurityGroupId>
```

Then pass the resulting `MasterSecretArn` back to the service as `Secret1Arn`.
Giving the application permissions is `TaskRoleArn` plus a managed policy.

## Splitting it up

One stack for everything is right while a service is small. Two things eventually
argue for splitting:

- **Lifetime.** The VPC and the ECR repository outlive the service many times
  over. Keeping them in the same stack means a teardown takes your image history
  with it (both carry `DeletionPolicy: Retain`, so they survive — but they become
  orphans nothing manages).
- **Blast radius.** A change to the service is a change to a stack that contains
  your network.

The split that works: `foundation` (VPC + registry, deployed rarely) and
`service` (everything else, deployed constantly), with the service stack taking
`VpcId` and `SubnetIds` as parameters.

See [`examples/basic`](examples/basic) for a parameter set you can deploy as-is.

### Parameters

| Parameter | Description | Type | Default |
|-----------|-------------|------|---------|
| `NamePrefix` | Prefix for every resource in the stack. Must be unique per account and region. | `String` | **required** |
| `Environment` | Environment this stack deploys.<br>Allowed: `dev`, `staging`, `prod` | `String` | `dev` |
| `ImageUri` | Container image to run, tagged with a commit SHA. On the very first deploy the ECR repository this stack creates is empty, so point this at a public placeholder image, push your own, then update. See the README. | `String` | **required** |
| `ContainerPort` | Port the application listens on. Injected as PORT. | `Number` | `8080` |
| `HealthCheckPath` | Path returning 200 when the application is ready to serve. It must not depend on a database - a health check that fails when a dependency is slow turns a degradation into an outage by removing every target. | `String` | `/healthz` |
| `HostedZoneId` | Route 53 zone for the certificate and the alias record. | `AWS::Route53::HostedZone::Id` | **required** |
| `DomainName` | Public hostname, e.g. api.example.com. Must be inside HostedZoneId, or the certificate never validates and the deploy hangs. | `String` | **required** |
| `Cpu` | Fargate CPU units per task (1024 = 1 vCPU).<br>Allowed: `256`, `512`, `1024`, `2048`, `4096` | `String` | `512` |
| `Memory` | Memory per task in MiB. Must be a legal pairing with Cpu. | `String` | `1024` |
| `MinCapacity` | Autoscaling floor. Two survives a task replacement without reaching zero. | `Number` | `2` |
| `MaxCapacity` | Autoscaling ceiling, and your cost cap under a traffic spike. | `Number` | `10` |
| `TargetRequestsPerTask` | Requests per minute per task the scaler holds. This is the best signal for a latency-sensitive HTTP service. 0 falls back to CPU-only scaling. | `Number` | `500` |
| `VpcCidr` | IPv4 range for the VPC this stack creates. | `String` | `10.0.0.0/16` |
| `AvailabilityZoneCount` | AZs to spread across. Three in prod.<br>Allowed: `2`, `3` | `String` | `2` |
| `NatGatewayMode` | Egress posture for the private subnets. See foundation/vpc - this is the largest fixed cost in the stack.<br>Allowed: `none`, `single`, `per-az` | `String` | `single` |
| `AlarmEmail` | Address that receives alarms. The subscription must be confirmed by clicking the link in the email; until then the alarms are silent. | `String` | `""` |
| `LogRetentionDays` | Retention for the application log group.<br>Allowed: `1`, `3`, `5`, `7`, `14`, `30`, `60`, `90`, `120`, `150`, `180`, `365`, `400`, `545`, `731`, `1827`, `3653` | `Number` | `30` |
